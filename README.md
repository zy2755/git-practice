### 2026-09-19 14:52 — 真正关掉手机浏览器的「自动反色」（找到官方写法了）

- 背景：上一版（11:11）加的三处加固发布后，和田的小米 15 上**依然**闪屏、浅色皮肤依然被深色盖住，而且在浏览器里**找不到**"网页深色适配"这个开关，没法确认是不是它在捣乱。
- 关键纠错：上一版把 `color-scheme` 写成 `light dark`，想表达"深浅我都能处理，你别插手"——**方向是反的**。查了 Chrome 官方文档《自动深色主题》（Auto Dark Theme）：浏览器**只认 `only` 这个关键字**才算"明确谢绝"。
  - `color-scheme: light` → 浏览器理解为"这页只会浅色"→ 热心地替你翻黑（**就是被反色的根源**）
  - `color-scheme: light dark` → 仍保留"可以覆盖"的权力 → 照样翻黑
  - `color-scheme: only light` → **官方认可的 opt-out**，浏览器一下都不改
  - 官方还特别说明：用 meta 标签声明的好处是"能从根上阻止自动反色被应用，否则会有『深色内容闪现』"——正好对上和田说的"切换时闪一下"。
- 本轮改动：
  1. `index.html`：`<meta name="color-scheme">` 由 `light dark` 改为 **`only light`**，`supported-color-schemes` 留 `light`（Safari 的旧属性不认 `only`）；新增 `darkreader-lock` / `nightmode:disable` / `forceDarkMode:disable` 三条各家浏览器的"别动手"约定。
  2. `theme.css`：`:root`、暖米、薄荷三套浅色皮肤都补 **`color-scheme: only light`**（保留上一行的 `light` 做老浏览器兼容）；深夜皮肤补 `color-scheme: only dark`；**删掉**上一版那个方向写反的 `@media (prefers-color-scheme: dark)` 补丁块（原地留了注释记这个坑）。
  3. `index.html` 的换肤逻辑：`<head>` 抢首帧脚本和底部 `setTheme()` 都顺手把那条 meta 同步成 `only light` / `only dark` —— 手动点到浅色皮肤那一下必须同时把"谢绝反色"改回去，否则浏览器下次重绘又会替我们翻黑。
  4. 新增**自检提示**：`#autoDarkHint`。用 Chrome 官方文档里那段探测法（造一个纯白小方块读它算出来的颜色，不是纯白就说明浏览器在反色），命中时页脚才冒出一行「检测到浏览器正在自动反色，页面配色可能不准」，并给 `<html>` 加 `.auto-dark` 类方便 F12 核对。有了它，"是不是那个功能在捣乱"从此不用靠猜。
- 验证：无头 Edge 实测四套皮肤算出来的 `color-scheme` 已是 `light only` / `light only` / `light only` / `dark only`；整站无头加载一遍，导航 5 项、4 张卡片、「这个速度还行」等文案全部正常，页脚驱动文案只有一条，`#autoDarkHint` 保持隐藏（说明未命中反色），`#buildTag` 正常填出时间。
  - 说明：`--force-dark-mode` 在无头 Edge 里没能复现出真正的反色效果（对照页也不变色），所以**这条修复没法在电脑上百分百复现验证**，得靠和田在小米 15 上实测。
- 版本号：`theme.css?v=6 → v=7`（`index.html` 也跟着改了，所以这次两头都要等缓存）。
- **15:04 已发布**（和田说"新版本发吧"）。
- 和田补充的线索（15:04）：他手机里"颜色反转 / 模拟颜色空间"**本来就是关的**；而他实测发现**只有把浏览器选成「跟随系统」或「夜间模式」时才会闪**，选成日间就不闪。→ 这进一步坐实是**浏览器自带的深色渲染**在动手（它只在浏览器自身处于深色时才介入），而不是系统无障碍或页面代码的问题。这正是 `only light` 要对付的那个东西。
- **✅ 15:20 和田确认：好了，浏览器夜间模式下也能正常切换了。** 这场从早上排查到下午的"手机深色闪屏 / 浅色皮肤被反色"，最终就是靠 `color-scheme: only light` 这一个关键字解决的。留下的两条经验：①"声明支持深色"和"谢绝自动反色"是两回事，浏览器只认 `only`；②以后遇到"只在特定环境才复现"的怪象，先想办法让页面自己把异常报出来（那个 `#autoDarkHint` 自检），比来回截图猜要快得多。
- 给和田的手机侧排查线索（如果提示条真的冒出来了，就是浏览器设置的问题，不是页面代码）：
  - **小米浏览器**的深色开关不在"网页深色适配"这类名字下，而是藏在 **「我的」（个人中心）→ 夜间模式 → 选「日间模式（浅色）」**；系统深色模式不会自动同步这个开关，两边要分别看。

### 2026-09-19 13:18 — 页脚加「最近更新」时间戳（用来自查缓存）

- 起因：普通访客（包括我们）分不清"网站没更新"和"自己拿到的是缓存里的旧副本"，来回排查很费劲。
- 做法：页脚加一行 `#buildTag`，由脚本读取 `document.lastModified`（浏览器从响应头拿到的"这个文件的最后修改时间"）自动填成「最近更新 YYYY-MM-DD HH:MM」。**不用手写日期，也不会忘记更新**；读不到时保持「—」，不编假日期。
- 用法：打开页面先看页脚那行时间。时间旧 = 拿到的是老副本（缓存问题）；时间新 = 服务器上就是这版。
- 样式：`.build-tag` 比页脚正文再淡一档（opacity .72），像一枚不抢眼的小印记。
- 13:24 已发布；**13:45:49 线上根地址才刷成新版，这次发布到可见等了约 21 分钟**（上午那次是十几分钟）。
- 【重要结论 · 以后照这个来】托管侧**只缓存 `.html` 这一种文件**，其它扩展名（`data.js` / `theme.css` / `README.md` / `og-image.js`）全是直通、发布即生效；而且 `/` 和 `/index.html` 是**两份独立的缓存，各自过期、时间还不同步**（这次 `/` 先刷新，`/index.html` 反而落后）。
  所以最省事的做法是：**让每次改动都别落在 `index.html` 上** —— 文案改 `data.js`（带 `?v=N`）、颜色改 `theme.css`（带 `?v=N`）、逻辑尽量挪进独立的 `.js`；`index.html` 越稳定越好，只在真改结构时才动它。这样发布就立刻生效，不用再等缓存过期。

### 2026-09-19 11:11 — 针对手机「深色模式切换闪屏 / 浅色皮肤被深色盖住」的加固

- 现象（和田的小米 15，系统深色下点切换）：①切换瞬间闪一下；②雾蓝/暖米/薄荷三套浅色皮肤看起来被深色覆盖。
- 排查：翻遍自己的 CSS，**没有任何规则会在浅色皮肤上写深色**，也不存在 `@media (prefers-color-scheme: dark)` 抢权；用无头 Edge 带 `--force-dark-mode --blink-settings=forceDarkModeEnabled=true` 渲染浅色版，页面确实被整体反色，效果与和田截图一致 → 判定是**手机浏览器自带的"强制深色网页"**在替我们反色（该功能只对"未声明支持深色"的页面生效，所以只有浅色皮肤遭殃；切到我们的深夜模式时浏览器发现页面自己会变黑，就不插手了）。
- 处理（三处）：
  1. `<head>` 加 `<meta name="color-scheme" content="light dark">` 与 `supported-color-schemes`，礼貌地告诉浏览器"本页自己会处理深浅色"，请它不要反色；
  2. `<html>` 补上 `background-color: var(--c-bg)` + 过渡（原来只有 body 有底色，切换皮肤瞬间浏览器会用默认画布色重画一帧，那一下就看着像闪屏）；
  3. `<meta name="theme-color">` 由 JS 跟着皮肤改（否则页面变浅、手机顶栏还是黑的，也像没切干净），并给 `#themeToggle`、`.skin-pill` 补 `-webkit-tap-highlight-color: transparent`（手机上点按钮默认会闪一下高亮块，也会被当成闪屏）。
- 验证：`.skin-pill` 点击后 `theme-color` 与 `--c-bg` 同步（暖米 #fbf8f3、深夜 #141922），四套配色渲染正常。**注意**：读 `--c-bg` 必须在改完 `data-theme` 后同步读，放进 `requestAnimationFrame` 里反而可能读不到（无头环境下 rAF 不执行），而 `background-color` 有过渡、读它只会拿到动画中间值。
- 待和田在手机上确认效果；若仍被反色，需在浏览器里关掉「夜间模式 / 网页深色适配 / 简化深色模式」再试，以确认是不是浏览器侧的行为。
- 12:24 已发布上线。本轮只改了 `index.html`，`theme.css` / 壁纸 / `data.js` / `og-image.js` 都没动，所以**没有升版本号**（升了也是白升）。
- 一条实测到的缓存规律（以后遇到"发了但没刷新"照着看）：托管域名的 `/` 和 `/index.html` **是两份独立的缓存**。这次发布后立刻抓取：`/` 返回旧版（`eo-cache: HIT`，23754 字节），`/index.html` 已经是新版（`eo-cache: MISS`，25166 字节）。也就是说发布本身是成功的，只是首页那条缓存要等它自己过期。加了 `?cb=时间戳` 也能立刻拿到新版。**排查时先抓 `/index.html`，别被 `/` 的旧内容骗了。**

### 2026-09-18 22:40 — 修 data.js 改文案不显示的问题，顺带把写法做得更宽松

- 现象：改 data.js 里「来在线看动漫」那条后，链接后面的「，这个速度还行」整段不显示。
- 原因：那一行写成了 `{ ..., linkText: "稀饭动漫", text: ",这个速度还行" }` —— 后面的内容借用了 `text` 这个字段名，但渲染时 `text` 只在链接**前面**显示，所以链接后的字就没地方放（另外句首逗号也应是中文的「，」）。
- 修法：改用 `tail` 字段写链接后面的内容 —— `tail: "，这个速度还行"`，显示为「这是稀饭动漫，这个速度还行」。
- 顺手增强：渲染脚本新增支持 `rest` 字段（一长句里把网址放 `link`、剩下的话直接放 `rest`，不用拆成前后两段），并在 `data.js` 顶部写清四个字段的用法和一个完整例子。
- 这类改动的排查口诀：**data.js 改完，先看"哪个字段名"有没有写对** —— 可用的就 `text` / `link` / `linkText` / `tail` / `rest` 五个，写错的字段不会报错，只会静静地不显示。
